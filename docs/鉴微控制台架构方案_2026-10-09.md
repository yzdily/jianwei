## 0. 结论先行

**架构不用换，方向已经对了——把这条"零依赖原生 SPA"路线收口成完整分层即可。**

现状：前端已经从单文件 `index.html` 拆成了 `tokens/shell/components.css + api.js/ui.js + views/*.js + app.js`，采用 `JW` 命名空间 + `JW.viewList` 注册表 + hash 路由，全部接后端真实 API（未提交，working tree 里）。
**这本身就是选定的架构**——它不是"临时凑合"，而是与项目定位（安全产品 · 内网/离线可用 · 零依赖）一致的自觉决策。

所以"用什么架构完善源码"的答案是：

> **五层原生分层架构（外壳 / 视图 / UI 原语 / API 客户端 / 设计 token）+ 契约层（data-testid + OpenAPI + 契约测试）。
> 不引入 React/Vue，不加构建链。把 demo 的缺口按"视图模块 + 后端路由"两件事补齐。**

## 1. 目标架构（五层 + 一契约）

```
┌─ 表现层 ────────────────────────────────────────────────┐
│ L1 外壳 Shell     index.html + app.js                    │
│                   hash 路由 · 导航渲染 · 用户卡 · 信息弹窗  │
├─ 视图层 View ──────────────────────────────────────────┤
│ L2 视图模块       js/views/*.js                          │
│                   一个 demo 视图 = 一个文件                │
│                   自注册到 JW.viewList，实现 mount()/refresh()│
├─ 原语层 UI ────────────────────────────────────────────┤
│ L3 UI 原语        js/ui.js                               │
│                   $ $$ esc toast modal kpi empty          │
│                   findingsTable mdToHtml addArtifact      │
├─ 通道层 API ───────────────────────────────────────────┤
│ L4 API 客户端     js/api.js                              │
│                   getJSON postJSON postForm getText sse   │
│                   唯一出口，前端不直接 fetch 硬编码路径       │
├─ 皮肤层 Tokens ────────────────────────────────────────┤
│ L5 设计 token     css/tokens.css → shell.css → components.css│
│                   demo §07 设计系统 = 唯一事实源            │
└─ 契约层 Contract ───────────────────────────────────────┘
    data-testid 锚点 · OpenAPI 快照 · tests/test_web_console.py
```

**为什么是"注册表 + 按需挂载"而不是"每页一个 HTML"：**
- 视图清单的唯一事实源在 JS 模块里（`JW.viewList`），HTML 不重复声明 → 加视图只改一个文件；
- section 按需 `createElement` 挂载，`mounted` Set 记忆已挂载，重访走 `refresh()` → 无重复 DOM、无过期数据；
- 这是"单页内的微前端"：每个视图自治，但共享外壳、UI 原语与 API 通道。

## 2. 原生 vs 框架：为什么保持原生

| 维度 | 原生（现状） | React/Vue 迁移 |
|---|---|---|
| 依赖 | 0（`test_index_has_no_external_cdn` 断言无 CDN） | 需构建链 + node_modules |
| 部署 | `FileResponse` 直接托管静态文件 | 需 dist 产物 + 构建步骤 |
| 离线/内网 | 天然满足（安全产品刚需） | 需额外配置 |
| 与 212 既有测试 | 契约测试已断言资源可达性 | 需重写测试与 CI |
| 单人非前端背景维护 | 心智负担低，改哪看哪 | 引入概念债 |
| 复杂度上限 | 适合"表单 + 表格 + 日志流"控制台 | 适合复杂交互/状态树 |

**判断**：鉴微控制台的交互形态是**表单发起 → 结果表格 → 流式日志 → 报告下载**，属于原生能覆盖的甜区。demo 里没有任何需要虚拟 DOM / 组件状态树 / 复杂路由的形态。**保持原生，但纪律要立起来**（见 §6）。

## 4. 后端需要补的契约（对齐 demo 的 G 通用功能）

demo 的「权限管理」是**纯前端模拟**，仓库**没有任何 RBAC / 报告归档 / 观测聚合**后端。要"真"起来，需新增三个 router（都挂到 `create_app()`，保持单应用工厂）：

| 新增 router | 端点 | 用途 | 对应 demo |
|---|---|---|---|
| `web/api/auth_api.py` | `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me` | 会话与身份 | 头像菜单 / 退出登录 |
| `web/api/rbac_api.py` | `GET/POST /api/users`、`/api/groups`、`/api/roles` | 子账号/用户组/角色 | G 四个 Tab |
| `web/api/report_store_api.py` | `GET /api/reports`（归档列表）、`GET /api/reports/{id}` | 报告库与溯源 | 04 报告中心归档 |

**同时必须收口的老债**：`web/api/skill_upload.py` 仍是一个**独立 app 工厂**（`_build_app()`，端口 8099），这是「双入口」问题的根。Phase 1 D1 要做的就是把它的路由并入 `create_app()`，`/` 只留一个。

## 6. 开发铁律（新增视图时不可破）

1. **一视图一文件**：`js/views/<id>.js`，末尾 `JW.viewList.push({id,no,name,desc,mount,refresh?})`，不得在 HTML 里重复声明视图。
2. **API 只走 `JW.api`**：禁止视图里裸写 `fetch("/api/...")`（`health.js` 的探活是唯一豁免，因为要读原始 status）。
3. **所有进 innerHTML 的数据过 `esc()`**：接口与用户输入一律转义，防 XSS。
4. **所有可交互元素带 `data-testid`**：E2E 不靠文本定位。
5. **加视图只改两处**：`views/` 新文件 + `index.html` 的 `<script>` 列表；导航自动出现（注册表驱动）。
6. **数字不造假**：拿不到真实数据就显式 `empty("…")` 说明原因，不写死演示值（现有代码已在守这条）。
7. **不引外部 CDN / 字体**：离线可用是硬约束，由 `test_web_console.py` 断言守住。
